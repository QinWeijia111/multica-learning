## Learning Outcome

读者完成本章后，应能解释 wakeup 为什么只是低延迟提示、polling 为什么仍是正确性后盾、claim 怎样把 durable `queued` record 原子地交给一个 Runtime；能区分 Daemon machine capacity、Agent concurrency 与同一 Agent 对同一工作目标的序列化边界，并能分析重复提示、并发轮询与 claim response 丢失时为什么不会简单地产生两个合法执行者。

## New Mental Model

任务发现与执行所有权是两件事：wakeup / polling 只触发“去检查”，数据库 claim 才在受约束的状态转换中授予一代执行权；Server 端容量与序列化约束决定记录是否可 claim，Daemon 端 slot 预留决定机器是否有位置接收它。它取代“谁先收到 WebSocket 消息谁就拥有任务”和“轮询返回一条 row 就等于已经安全执行”两种误解。

## Terminology Budget

- **wakeup hint（唤醒提示）**：通知 Daemon 现在值得检查工作；不携带执行权。
- **polling / safety poll（轮询 / 安全轮询）**：Daemon 主动查询 durable queue 的后盾路径。
- **claim（领取）**：把符合条件的 `queued` row 原子地推进为 `dispatched`，形成一代执行权。
- **capacity slot（容量槽）**：Daemon 或 Agent 当前允许接纳的并发位置；两层上限解决不同问题。
- **claim generation（领取代次）**：由本次 dispatch 时间等字段标识、可被后续 start / finalization CAS 校验的一次领取尝试。

Runtime、Daemon、Agent、Run / task、`queued`、`dispatched`、`running` 沿用前章，不计入新增术语预算。

## Completion Test

给读者一个场景：同一 queued task 的 wakeup 被重复发送，两台 Server 同时处理 claim 请求，其中一次 response 丢失，Daemon 还有多个空闲 slot，但目标 Agent 的并发额度只剩一个。读者应能说明提示为何不授予所有权、谁在什么边界赢得 `queued → dispatched`、哪些容量 / 序列化门会阻止其余候选、为什么丢失 response 不应立刻 HTTP double-claim，以及应该去 M07 / M13 的哪些章节继续验证生命周期和故障恢复。
