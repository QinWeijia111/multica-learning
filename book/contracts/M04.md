本契约在广泛源码研究前锁定 M04 的既有 Reader Question 与章节责任。它不把四类产品入口预设成同一个函数，也不提前展开 M05 的 durable-task 内部模型或 M06 的 claim 算法。

## Identity

- **Module**：M04

- **Part**：Part II — 一次 Run 如何被调度
- **Architecture status**：`NEAR_TERM_FROZEN`

## Reader Question

Agent 为什么开始工作？

## Prerequisites

- M01 已让读者看过一次 Issue 分配如何走到本地 Coding Agent。

## Learning Outcome

读者完成本章后，应能区分 Issue 分配、评论 mention / 继续讨论、直接 Chat 与 Autopilot 四类显式触发，解释它们怎样先各自解析目标、权限与上下文，再形成可由 Runtime 领取的一次执行；同时能指出“汇入执行主线”不等于四类入口共享完全相同的 handler、上下文或持久字段。

## New Mental Model

不同入口负责回答“为什么现在要让谁工作、携带什么上下文”，共同执行主线负责回答“如何把一次已准入的工作交给绑定 Runtime”。它取代“Agent 一直在线监听通知”以及“所有 trigger 只是同一个 HTTP endpoint 的别名”两种误解。

## Terminology Budget

- **Trigger（触发）**：明确导致一次 Agent 执行被创建或安排的用户 / 系统动作。
- **路由（routing）**：从入口确定实际执行 Agent 及其上下文；避免把 mention 理解成 inbox 通知。
- **汇流（convergence）**：不同入口最终形成同类可执行记录并通知目标 Runtime；不表示入口实现完全相同。
- **provenance（触发来源）**：记录这次执行由哪类动作、哪条评论 / Chat / Autopilot run 引起，便于解释差异。

Issue、Run/task、Agent、Runtime、Daemon 沿用 M01–M03，不计入新增术语预算。

## Evidence Requirements

- **SOURCE**：每类入口至少追到目标解析、task insert 与 Runtime notify；所有实现主张固定到完整上游 SHA。
- **DOCS**：四类产品 taxonomy 由官方 `triggering-agents` / `how-multica-works` / `tasks` 页面支持，并与所查源码逐类对照。
- **EXPERIMENT**：只有静态源码不能区分入口语义时才运行最小实验；缺少凭据或基础设施时明确记录限制。
- “共同主线”必须逐项写出共同字段 / 行为和差异；不能从相同表名推导完全相同的上下文、权限或幂等语义。
- Source Map、调用 / 状态路径、evidence gap 与 unresolved questions 必须可供 Writer 无需重做广泛研究即可使用。

## Completion Test

给读者四个场景：把 active Issue 分配给 Agent、在评论中 mention 另一个 Agent、发送直接 Chat、由 Autopilot schedule 触发。读者应能说明每个入口先解决什么路由 / 上下文问题、最终在哪个执行边界汇合、哪些来源字段仍不同，并解释为什么 Runtime wakeup 不等于已经获得执行权。

## Editorial Notes

- Reader Question 与工作标题保持 Book Architecture 的既有文字，不作改写。
- “四类”按官方产品 taxonomy 冻结为 Issue assignment、comment mention / continuation、direct chat、Autopilot；reply 与 status promotion 是相应族内语义，不扩为第五类。
- 本章讲“触发来源不同、执行主线可汇合”；durability 与 claim 正确性必须停在边界句，避免抢写 M05–M06。
