## Reader Question

## Learning Outcome

读者完成本章后，应能区分 Issue 与 Run 的生命周期，解释一次触发为何需要独立、持久、可追踪的执行记录；能识别该记录承载的目标、来源、状态、结果与重试 / 重跑血缘，并说明 TaskService 与数据库状态转换各自承担什么责任，而不把通知或内存中的函数调用误当作执行事实。

## New Mental Model

Run 是“一次执行尝试”的耐久事实：Issue 可以长期演进并包含多次执行，而每次 Run 有独立身份、状态、来源和结果。TaskService 编排这些记录的创建与转换，数据库记录才是跨请求、进程和 Runtime 边界保存的事实。它取代“Run 只是一次 HTTP 请求 / goroutine”以及“Run 完成就等于 Issue 完成”两种误解。

## Terminology Budget

- **Run（运行）**：面向用户的一次 Agent 执行记录；不是 Issue 本身。
- **durable task（耐久任务）**：跨请求和进程保存、可恢复读取和推进的一次执行事实。
- **attempt（尝试）**：自动 retry 链上的执行序号；每次尝试仍是独立记录。
- **lineage（血缘）**：通过 retry / rerun 指针连接新旧执行记录而不覆盖历史。
- **terminal state（终态）**：`completed`、`failed` 或 `cancelled`；描述本次执行结束，不判断 Issue 目标是否完成。

Issue、Agent、Runtime、Trigger 沿用前章，不计入新增术语预算。

## Evidence Requirements

- **SOURCE**：产品 Run 到 task 实现的映射、持久字段、状态转换与 lineage 必须绑定固定上游完整 SHA，并定位到具体 symbol / SQL region。
- **DOCS**：Run / Issue 区别、生命周期和 retry 产品语义须与当前官方 Runs 文档对照；若与源码不同，保留差异。
- **EXPERIMENT**：只有静态源码与文档不能区分关键语义时才做最小实验；没有必要时明确记录未运行实验。
- “durable”不能只由表名推断；至少验证持久 insert、后续独立读取 / 转换、历史保留与通知边界。
- Source Map、调用 / 状态路径、verified conclusions、unresolved questions 和 M06 / M13 边界必须足够 Writer 直接使用。

## Completion Test

给读者一个同一 Issue 先执行失败、自动 retry、随后由用户手动 rerun 并最终把 Issue 标为 done 的场景。读者应能说明其中有几条独立 Run、旧记录为何不被覆盖、自动 retry 与人工 rerun 的血缘和意图有何不同、Run 的终态为何不能决定 Issue 是否完成，并指出“谁获得 queued Run”的问题应去 M06 验证。
