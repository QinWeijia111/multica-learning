# 教学流程

Multica Learning 面向懂编程、但可能没有系统学习过 Agent runtime、分布式系统、后端基础设施或大型生产代码库的中文读者。教学目标不是展示源码有多复杂，而是让读者从一个可观察问题出发，建立足够小的模型，再用真实源码验证并修正它。

## 推荐顺序

```text
具体问题
→ 为什么需要
→ 最小心智模型
→ 真实实现
→ Source Map
→ 调用链
→ 关键代码
→ 设计原因
→ 易混点
→ 工程启示
→ 快速复习
```

### 具体问题

从一次操作、一个现象或一个工程疑问开始。问题应足够具体，使读者能判断本章最终是否回答了它。

### 为什么需要

说明系统要解决的约束或协作问题。只引入理解后续机制所需的背景，不先铺陈整套架构。

### 最小心智模型

用少量节点、关系或状态建立第一版模型，并明确标注为“概念模型”。模型是教学脚手架，不等于真实源码中的命名和边界。

### 真实实现

把概念节点逐一映射到当前 Multica commit 中已验证的模块、类型、函数、数据表、状态或协议。遇到无法一一对应的概念，解释差异，不强行配对。

### Source Map

列出回答本章问题所需的关键文件与 symbol，并简述各自作用。Source Map 是导航和证据入口，不是目录树清单。

### 调用链

先讲主执行路径：入口、关键调用或状态转换、结果路径。让每一步都能回到研究证据。图比长段调用链文字更清楚时，优先使用图。

### 关键代码

只选能解释机制转折点的短片段。先说读者要观察什么，再展示代码并解释。简化内容必须标注为伪代码或简化表示。

### 设计原因

区分有直接证据的设计约束与作者自己的工程解释。没有证据时，不猜测 Multica 作者的主观动机。

### 易混点、工程启示与快速复习

集中澄清产品词汇与实现词汇、概念模型与源码实体、通知与状态事实等容易混淆的边界。工程启示应从本章机制自然推出。快速复习用于读者自测，不重复整章。

## 先主路径，后分支

先完整讲清 happy path，再按理解价值补充：

1. 常见可选路径；
2. 关键失败路径与恢复方式；
3. 只在特定部署或配置下出现的边界情况。

若分支会打断主线，把它放入独立小节、旁注或后续章节。不要把每个 edge case 混入主路径，使读者无法看清系统的基本因果关系。

## 避免四种组织方式

- **按目录逐个讲解**：目录边界未必对应一个可理解的运行机制，容易让读者记住文件名却不知道系统如何工作。
- **大段粘贴源码**：源码量会掩盖真正的控制流、状态变化与设计约束，也让证据难以聚焦。
- **从几十个类型定义开始**：读者还没有问题框架，无法判断哪些类型重要。只在调用链需要时引入类型。
- **把所有分支塞进 happy path**：主因果链会被错误处理、兼容逻辑和可选配置淹没。先建立稳定骨架，再分层添加复杂度。

章节可以偏离推荐顺序，但应有明确教学理由，并持续保持“问题—模型—实现—证据”的可追溯关系。
