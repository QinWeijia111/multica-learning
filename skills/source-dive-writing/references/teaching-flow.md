# 教学流程

Multica Learning 面向懂编程、但可能没有系统学习过 Agent runtime、分布式系统、后端基础设施或大型生产代码库的中文读者。教学目标不是让读者先记住源码符号，而是让他先能用自己的话解释问题、机制和设计取舍，再按需进入真实实现。

## 推荐顺序

```text
可观察问题
→ 一句话答案
→ 朴素方案为什么不够
→ 最小心智模型
→ 一个端到端具体旅程
→ 逐个机制解释
→ 架构综合
→ 设计含义
→ 易混点与快速复习
→ 可选的源码导航附录
→ 精确调用链 / Source Map
→ 源码基线与证据
```

这不是强制目录。章节可以因教学需要合并、拆分或调整小节，但不得把精确 symbol、Source Map 或完整调用链默认放回读者尚未理解机制的早期主线。

### 可观察问题与一句话答案

从一次操作、一个现象或一个工程疑问开始。问题应足够具体，使读者能判断本章最终是否回答了它。紧接着先给自然语言答案，让读者知道整章会证明什么，不用读完源码才能猜出结论。

### 朴素方案为什么不够

先描述读者最容易想到的简单做法，再指出它在哪个真实约束下失效，例如进程边界、并发竞争、断线恢复或持久性。只介绍后续机制真正要解决的约束，不先铺陈整套基础设施。

### 最小心智模型

用少量角色、关系或状态建立第一版模型，并明确标注为“教学模型”。标签优先表达中文架构含义。模型是教学脚手架，不等于真实源码中的命名和边界。

### 一个端到端具体旅程

选择一个有明确起点和结果的例子，让同一个任务、请求或状态依次穿过主要角色。主线使用语义阶段，例如：

```text
服务端保存待执行任务
→ 提醒 Daemon 有新工作
→ Daemon 请求领取
→ 数据库确认执行权
→ 本地启动执行
```

不要用一串函数名代替这个旅程。先完整讲清 happy path，再按理解价值补充可选路径、关键失败路径和恢复方式。

### 逐个机制解释

每节只回答一个读者问题，例如“为什么提醒不等于获得执行权？”。推荐按需使用以下层次：

1. 自然语言解释；
2. 教学图或明确标注的简化伪代码；
3. 聚焦的真实源码片段；
4. 简短的“源码定位”。

不是每节都需要四层。使用足以解释机制的最少层次；源码证据必须在读者侧解释之后出现。

#### 教学伪代码

教学伪代码用于暴露关键控制流、状态转换、分支、循环、数据移动或角色交互。可以暂时省略校验、日志、兼容分支、重复错误处理、管道代码和无关配置，但必须：

- 显著标注“简化伪代码”或“教学伪代码”，不得伪装成上游源码；
- 与已验证研究的控制流和状态语义一致；
- 不增加研究没有支持的行为；
- 只抽象当前解释不需要的生产细节。

若伪代码已经足以回答读者问题，不必为了“展示源码”强行追加生产代码。

#### 真实源码片段

真实源码只在能证明或加深一个具体机制时出现。展示前先告诉读者要观察什么，例如：

> 这段 SQL 暂时只看两个地方：`FOR UPDATE SKIP LOCKED` 与 `queued → dispatched`。

片段应聚焦一个教学点。通常 5–25 行足够，但教学价值比机械行数更重要。省略内容时明确标记；不要让初学者从一个大型生产函数中自行反推架构。

#### 源码定位

机制解释后的定位信息保持简短、相关且可操作：

> 源码定位
>
> - 路径：`path/to/file.go`
> - Symbol：`ExactSymbol`
> - 作用：这里验证了数据库在认领时完成状态转换。

不要在普通段落中倾倒多个无关 symbol。完整导航留给附录。

### 架构综合与设计含义

在读者理解各机制后，再把角色、状态与边界合成完整架构。区分直接证据支持的设计约束与作者自己的工程解释；没有证据时，不猜测 Multica 作者的主观动机。

### 易混点与快速复习

集中澄清产品词汇与实现词汇、教学模型与源码实体、通知与状态事实等边界。复习应检查读者能否不用函数名解释架构、说明各机制为何存在，并知道何时进入源码附录；不要逐段重复正文。

## 可选的源码导航附录

Source Map 和精确调用链仍是 source-grounded 章节的必需证据，但默认属于章节末尾的导航层。它们服务于已经理解机制、准备打开源码的读者，而不是承担首次教学。

附录通常依次包含：

1. Source Map：回答本章问题所需的关键文件、准确 symbol、作用与证据等级；
2. 精确执行 / 调用链：入口、关键调用或状态转换、结果路径；
3. 源码基线与研究依据：仓库、完整 commit SHA、研究产物和未决问题。

只有“精确调用顺序本身”就是章节学习目标时，才把精确调用链提前；此时仍应先给语义阶段，再映射到 symbol。Source Map 不是目录树清单，也不应重复正文已经解释清楚的架构。

## 先主路径，后分支

先完整讲清 happy path，再按理解价值补充：

1. 常见可选路径；
2. 关键失败路径与恢复方式；
3. 只在特定部署或配置下出现的边界情况。

若分支会打断主线，把它放入独立小节、旁注或后续章节。不要把每个 edge case 混入主路径，使读者无法看清系统的基本因果关系。

## 避免五种组织方式

- **按目录逐个讲解**：目录边界未必对应一个可理解的运行机制。
- **用 symbol 链承担首次解释**：读者会记住函数名，却无法说明系统在做什么。
- **大段粘贴源码**：生产细节会掩盖控制流、状态变化与设计约束。
- **从几十个类型定义开始**：读者还没有问题框架，无法判断哪些类型重要。
- **把所有分支塞进 happy path**：主因果链会被错误处理、兼容逻辑和可选配置淹没。

## 教学评审门槛

若新读者必须先记忆源码函数名才能理解系统行为，章节应评审失败。评审者至少应能回答：

- 不记任何函数名，我能否解释整体架构？
- 我是否理解每个关键机制为何存在？
- 想检查实现时，能否找到准确路径、symbol 和完整调用链？
- 陌生术语是否只在真正需要时出现，并在首次出现时得到解释？
- 每张图是否解释一个概念，而不只是把标识符画出来？
- 只读正文与伪代码，是否已经能解释机制？真实源码是否只证明或深化一个明确教学点？
