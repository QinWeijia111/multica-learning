# Mermaid 项目约定

这些约定用于 Multica Learning 的教学图，不是 Mermaid 语法百科。

## ID 与标签

- 使用稳定、短小、只承担引用作用的 ID，例如 `server`、`daemon`、`queue`；不要把完整展示文案当 ID。
- 面向读者的标签优先使用自然简体中文。
- type、function、method、table、状态值、API / RPC 名等源码标识符保持原样，可在同一标签或附近正文中补充中文解释。
- 同类节点使用平行、一致的标签结构，避免有的写职责、有的写内部实现。

## 箭头

- 当语义并非显而易见时，标明 call、HTTP、WebSocket、RPC、事件、数据库读写、状态转换、通知或依赖。
- 标签应与证据支持的精度一致；不要把“发送消息”擅自具体化为未经验证的协议。
- 统一箭头方向的含义。sequence diagram 中按真实交互顺序排列；state diagram 中把触发事件写在转换上。
- 不用仅靠实线、虚线或颜色表达不确定性；同时提供文字说明。

## 布局与边界

- `LR` 适合少量节点的横向主路径；若在文章栏或移动端变得过宽，改用 `TD`、缩短展示标签或拆图。
- 使用 subgraph 表达真实的服务、进程、信任或职责边界，不把它当装饰框。
- 一张主教学图优先保留约 5–9 个有意义节点。节点过多时拆分视图，不缩小字体硬塞。
- 保持一个抽象层级；不要把服务、函数、数据库行和外部参与者无说明地并列。
- 避免依赖极宽布局、长单行标签或复杂交叉线；在目标文章宽度和移动端检查渲染结果。

## 主题与强调

- 不在单张图中硬编码装饰性 `fill`、`color` 或主题色；让站点 renderer 统一管理明暗主题与对比度。
- 需要强调时优先使用文字、形状、边界、位置或线型，并确保意义不依赖颜色。
- 仅在项目统一主题明确要求且同时验证亮色、暗色与对比度时添加样式。

## Caption 与文本 fallback

- 在每张非平凡图附近写一句明确 caption：说明问题、类别（`CONCEPTUAL` / `IMPLEMENTATION`）和核心结论。
- 在正文保留关键关系、状态和不确定性；Mermaid 不可用时，读者仍应理解必要结论。
- 图中标签保持精炼，把证据说明与细节放在邻近正文或 review 记录中。
